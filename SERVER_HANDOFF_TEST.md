# MOTO TECH — передача серверным специалистам (TEST ONLY)

Дата: 21.10.2026. Ветка развёртывания: `deploy/server-test-candidate` на основе `integration/storage-pilot`.

## Назначение
Подготовить закрытый тестовый контур на принадлежащем заказчику сервере HPE ProLiant / Proxmox в РФ. **Это не промышленный релиз. Не вводить реальную клиентскую информацию, ПТС или фотографии клиентов.**

## Состав
- `backend/api/main.py` — основной API, PostgreSQL.
- `backend/migrations/001_...025_*.sql` — SQL-схема (применять последовательно, в транзакциях там, где это поддерживается).
- `compose.storage-pilot.yml` и `backend/Dockerfile` — локальный Docker Compose.
- `docs/storage-server.html` — серверный интерфейс пилота.
- `backend/tests` — базовые тесты.
- `app.py` и `static/index.html` — **отдельный старый SQLite MVP**, не является основной серверной системой; не смешивать его базу с PostgreSQL автоматически.
- `docs/index.html` — отдельный демонстрационный интерфейс; не считать полноценным рабочим клиентом серверного API.

## Настройка тестового контура
1. В отдельной VM установите актуальную поддерживаемую ОС Linux, Docker Engine и Compose Plugin. Обновления безопасности включить.
2. Склонируйте именно данную ветку. Зафиксируйте commit SHA. Храните исходники в закрытом для публики каталоге.
3. Создайте `.env` на основе `.env.storage-pilot.example`. Создайте новые надёжные секреты. Файл `.env` никогда не отправлять в GitHub и не включать в архив исходников.
4. Запустите `docker compose -f compose.storage-pilot.yml up -d --build`. PostgreSQL не публиковать в интернет. API в Compose слушает 127.0.0.1:10000.
5. Создайте миграционный журнал; проверьте SQL-миграции 001–025 на **пустой тестовой БД** и сохраните логи. Сценарий в STORAGE_PILOT_SETUP.md описывает только 001 и 002; для актуальных API нужен аудит порядка всех последующих миграций.
6. Добавьте двух тестовых сотрудников с разными ролями согласно `backend/provision_initial_manager.py` и схеме; пароль не должен быть дефолтным.
7. Настройте отдельный HTTPS reverse proxy и точный `MOTOTECH_ALLOWED_ORIGINS`; внешний доступ только через VPN/allowlist. SSL/TLS, вход, выход, загрузка/возврат техники — проверить.
8. Диски для PostgreSQL и `photo_data` должны быть persistent; не использовать ephemeral volumes. Сделать резервную копию и **проверить восстановление** на отдельной VM.
9. Настройте журналирование, мониторинг места, ошибок API, состояния базы, срока сертификата и резервных копий.

## Безопасность и ограничения
- Публикация в интернет с персональными данными запрещена до аудита защиты и тестов.
- Требуются rate limit для авторизации, модель ролей, защищённая выдача фото, журналирование доступов, ограничения размера загрузки и проверка файлов.
- Ветка `develop/intake-photos-0.3` — конкурирующий SQLite прототип: **не сливать app.py в API PostgreSQL** без отдельного проектирования и тестирования.
- VIN и фото VIN необязательны. Обязательны ракурсы front/rear/left/right; дополнительные фото повреждений — с описанием.
- Проверить в API, что каждое бизнес-действие в серверном UI реально поддерживается и нет демо-only элементов.
- Render/внешние облачные базы не являются источником истины без документально подтверждённого экспорта и сверки данных. Не переносить реальные данные в тестовый контур.

## Миграция существующей тестовой версии — отдельный этап
1. Установить, какая именно тестовая версия сейчас фактически используется, её URL, доступную БД, файловые каталоги, схемы и число записей.
2. Снять неизменяемый backup исходной базы и файлов; записать контрольные суммы.
3. Составить таблицу сопоставления структур (клиенты, техника, ремонты, хранение, вложения, CRM, инвентаризация, пользователи, история).
4. Выполнить пробный импорт **обезличенных** данных и сверку ID, связей, сумм и количества файлов.
5. Только после аудита ролей, безопасности, готовности PRODUCTION и согласования даты провести перенос реальных данных; обеспечить план отката.

## Критерии готовности инфраструктуры
- Принят акт с IP/именами VM (без раскрытия секретов), CPU/RAM/disk, версиями Docker/PostgreSQL, схемой сети.
- Работает HTTPS в ограниченном доступе, закрыты DB/служебные порты.
- Все миграции проходят на новой БД; тесты выполняются успешно.
- Четыре обязательных фото; отсутствие VIN не блокирует приёмку; корректный отказ при отсутствии ракурса.
- Сохраняются/читаются фото после перезапуска контейнера; резервная копия реально восстановлена.
- Есть лог ошибок, результат security-review, список недоработок и понятный процесс последующих обновлений без потери данных.

## Не входит в данную передачу
Деплой в продуктив, перенос реальных данных, гарантии завершённости всех модулей и автоматическое обновление без регрессионных проверок.
